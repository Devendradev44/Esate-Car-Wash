# Estate Car Spa Frontend Implementation Plan

## Product constraints

- Frontend-only scope. Do not add or modify database, Prisma, backend services, or backend-owned business logic.
- Use the existing frontend mock state and local fixtures while backend integration is handled separately.
- Keep all user flows usable from frontend routes without requiring a backend response.
- Use a responsive black, grey, and yellow palette throughout public, customer, staff, and admin surfaces.
- Support four-wheeler vehicles only. Exclude every `Two Wheeler` record from the supplied vehicle dataset.
- Normalize vehicle categories for the booking and pricing flows: `Hatchback`, `Sedan`, `SUV`, and `Luxury`.
  - Map `Compact SUV`, `Large SUV`, `SUV`, and the dataset typo `SU` to `SUV`.
  - Preserve the supplied make and model names as display data.
  - Clean encoding artifacts and deduplicate records before loading the fixture.
- Do not rely on multiple auth cookies. During frontend-only development, use the existing persisted Zustand state as the single source of truth and remove cookie-based route guards.

## Current-state findings

- `src/proxy.ts` performs server-side role redirects and reads `mock_session`; it must be removed for the agreed client-side-guard approach.
- Login, signup, sidebar, and profile code write or clear `mock_session` directly. These writes should be removed to prevent cookie accumulation and keep auth state consistent with Zustand persistence.
- The current app has client hydration guards in several pages, but role authorization is still split between proxy logic and client navigation.
- The vehicle master currently contains only a few hand-written records in `src/lib/store.ts`; `src/lib/mockData.ts` contains an older commented fixture and does not represent the supplied dataset.
- `src/app/api/vehicles/route.ts` depends on an external API key and does not provide category filtering. It should not be a required dependency for frontend-only flows.
- `npm run build` currently passes.
- `npm run lint` currently fails with 46 errors and 8 warnings. Most app errors are repeated hydration effects, impure `Date.now()` calls during render, render-created components, untyped API responses, and a few unused values. The bundled `.agents` skill scripts are also included by the current lint command.

## Work plan

### 1. Establish the frontend-only boundary

- Remove `src/proxy.ts` and all cookie reads/writes used for route authorization.
- Add one shared client-side auth gate for protected customer, staff, and admin routes.
- Redirect unauthenticated users to `/login`.
- Redirect authenticated users away from `/login` and `/signup` to the route matching their role.
- Keep the guard client-only and compatible with Zustand persistence hydration.
- Leave backend-owned data contracts untouched. Use local fixtures or the existing mock store for frontend validation.

### 2. Standardize responsive black/grey/yellow design

- Replace blue, red, and green brand/status colors with yellow accents and neutral grey states.
- Define reusable color, spacing, radius, typography, focus, and disabled-state conventions in `globals.css`.
- Audit every page and shared navigation component for hardcoded palette classes.
- Make admin sidebar, customer/staff bottom navigation, forms, cards, tables, and modals usable at 360px, 768px, 1024px, and desktop widths.
- Use mobile card layouts where desktop tables would overflow; keep tables horizontally scrollable only when necessary.
- Add safe bottom spacing for fixed navigation and ensure buttons, inputs, and touch targets remain accessible.

### 3. Load and validate the four-wheeler vehicle dataset

- Add the supplied vehicle records as a typed local frontend fixture.
- Filter out all rows whose source category is `Two Wheeler`.
- Normalize category names into `Hatchback`, `Sedan`, `SUV`, and `Luxury`.
- Normalize `Compact SUV`, `Large SUV`, `SUV`, and `SU` to `SUV`.
- Remove or repair malformed characters and duplicate make/model/category rows.
- Generate stable IDs instead of using render-time timestamps.
- Verify the final fixture contains the expected four-wheeler records and zero two-wheelers.
- Use the same fixture in customer booking, customer garage, and admin vehicle master flows.

### 4. Harden frontend validation and interactions

- Add inline validation for names, phone numbers, email addresses, passwords, addresses, registration numbers, service selection, dates, and time slots.
- Prevent incomplete vehicle selections from reaching the booking submission path.
- Keep capacity and past-time checks in the frontend mock flow without making backend calls.
- Replace browser alerts with visible inline feedback where practical.
- Ensure logout clears only the frontend session state and navigates reliably.
- Preserve existing booking, cancellation, completion, service pricing, community, address, staff, and expense interactions while keeping them mock-only.

### 5. Verify routes, responsiveness, and regressions

- Run TypeScript/build checks after each major change.
- Run lint with the project-owned source scoped correctly; resolve app errors and either exclude bundled skill tooling or fix its configuration without changing skill source unnecessarily.
- Smoke-test public landing, login, signup, customer dashboard, booking, garage, addresses, profile, staff dashboard/profile, admin dashboard, bookings, vehicles, services, and settings routes.
- Test logged-out protected-route redirects, wrong-role redirects, authenticated auth-page redirects, and logout behavior.
- Test vehicle search, category filtering, make/model cascading, saved-vehicle selection, and booking price calculation.
- Test responsive layouts at 360px, 768px, 1024px, and 1440px.
- Confirm no `middleware` or `proxy` file remains and no auth cookie is created during the frontend-only flow.

## Acceptance criteria

- The app builds successfully with `npm run build`.
- Project source passes lint and TypeScript checks.
- No database, Prisma, or backend-owned code is changed.
- No `middleware.ts`, `middleware.js`, `proxy.ts`, or `proxy.js` route guard remains.
- Authentication and role checks work through the shared client-side guard.
- The UI uses only black, grey, yellow, white, and neutral accessibility states.
- All primary flows remain usable on mobile and desktop.
- Vehicle selectors contain four-wheelers only and expose the agreed categories.
- The supplied vehicle dataset is validated for category normalization, duplicates, malformed text, and two-wheeler exclusion.
- Frontend routes and mock interactions work without the external vehicle API or a backend service.
